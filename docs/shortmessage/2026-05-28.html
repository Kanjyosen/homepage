死とは何か・・・僭越だが
　前回の記事に反響...があったわけでもないですが，なんかTwitterが最近またAI活用，というよりかはAIによる人間のサイボーグ化の話で埋め尽くされているので，また話をば．
　率直に言いますが，私は技術職に就かなかったことに対して心底安堵しています．いや，これは本当に．というのも，現代のAI活用に私は到底ついていける気がしないのですが，少なくとも技術においては生成AIがかなり幅を利かせていることは最早逃げようのない事実です．そういう意味では，生成AIの発展を考えると本職技術者としての私は死んだに等しいというわけです．結局何って，古い方式から抜けることがかなり難しいということ．
　人間不信＜AI不信だと考えている人もいるようですが，私はそもそもとして1+1以外に信用できるものは厳密には存在しないと思っています．はっきり言えば，自分も他人も生成AIもどこかしらに間違いはあるということを思っています．勿論自分も刑事的前科がない人間としては上位になるくらい欠点や間違いばかりですが，他人，今この文章を読んでいるあなたにだって欠点や間違いは存在しますし，（もしかすればこの文章を戯れに読まされている）生成AIにも存在します．そして，見えない状態のそれを放っておくことがどうしてもできない．前回述べた「ものづくりが完全に黒箱の中」に到底耐えられないのが私です．
　自分で物を作ればある程度は何が欠点でその根源はどこかすぐ見当がつきますが，黒箱の中に入れられればどうしようもありません．特に大きなものになれば尚更で，自分のものとして使うならばその物を読んだ状態でなければ責任が取れない，いくらAIがデバッグできようとそのデバッグが今度は黒箱の中であれば結局検証のしようがない．言うなれば，不透明樹脂で固められたメーカオリジナルのICチップがよりにもよってその回路の中心的動作を担っているような状態としか私には見えないんです．もしくは，樹脂は削ればICチップの足にプローブでも当てればだいたい処理単体の信号が出せますから，まだましだと思います．生成AIの出力は或る意味統合されたものなのですから．
　さて，結局表題の「死」について殆ど話さずに来ましたが，私は結論から言えば「アウトバーンを遅い速度で走る性能の悪いオート三輪が速いし性能も良いトラックに轢かれた」みたいなもんだと思っています．いつまでも性能を上げないで結果速度も上げない．そうすれば後続がやってきて轢くのは物理的には当然の話だと思います．しかも技術の世界は今やアウトバーンですから，なおさらトラックは速度を上げています．実際色々とかまけていたのが自分というわけですし，どう考えてもそうなるわけです．しかしこの事故で失われるのは人命ではなく技術職として働く資格です．求められる性能などがどんどん上がって行く中でこういう事故で旧性能が駆逐されるのではないでしょうか．私も轢かれた一員です．（一応言っておきますが，この事故の過失は現代社会においては，特に技術の世界ではすべてオート三輪側にあるというのが，色々見た結論です．）
　我田引水の終末論的に言えば，この事故が多発したあとにトラックは突然動かなくなる，或いは借り物は急に返せだのもっとリース料を払えだの難癖をつけられる，そしてアンデッド・オート三輪がアウトバーンを走る，というのが或る意味私の悪意が抱える本望です．しかし当然社会はそうはなりません．結局トラックは走るし，いつの間にかエンジンを付け替えている．V8，V16，V32，V128，V256，V512，V1k...実際はもっと早く性能を上げているでしょうし，気筒の割にも上がるのでしょうが，兎も角そういう進み方で社会が進むわけです．そしてトラックは当然相対的に遅くなるオート三輪を見て苛立ち，嘲笑い，やがて轢くわけです．（前述に矛盾しますが，）これは世情の表現としては確度の高い話だと思います．
　ここまで駄々をこねてきましたが，もう一つ死ぬと思っていることがあります．ものづくりがゲームや動画視聴（≠動画評論）などの趣味と高度差をつけている土台です．実際，死ぬというより死滅していると思います．なにせ，作るというだけでは黒箱でも大多数の人は何も気にしないし私みたいなのに苛立って場合によっては手にかけるでしょうから． 　バイナリ・コーディングからプログラミング言語の転移は，プログラミング言語から生成AIへの転移と同等である，という指摘をよく見かけます．確かに黒箱化という意味では同じものですし，ものづくりを楽にしたという意味でも同じでしょう．（実際問題，昔大学の講義でバイナリ・コーディングを「二度とやりたくない」と言った教授がいました．なお，その教授は頭の回転が速く私のような愚図にはついていけないくらいの方でしたので，バイナリ・コーディングが如何に面倒なものだったか，少しばかりご推察頂けるかと思います．）ところが，個人的には若干の詭弁ではないかと思います．（思うだけですので，論考に達していない点をお許しいただければと思います．）というのも，バイナリ・コーディングはコンピュータ様に合わせてあまりにも細かすぎて人間には伝わらない処理が１単位...というか，そもそも単位があるんだかという世界で，プログラミング言語はそれなりに単純な処理（例えば極端な例では1+1，日常的な例だとint a = 0;だとかoctagon[7] = "end point"だとかかな？）が１単位の世界です．ただし，Pythonのtensorflowなどはやってみた感じこの法則性が若干崩れて黒箱寄りになっていると思いますが．兎も角，そこから生成AIの段階に飛ぶと複雑な物が１単位にすらなるわけです．A方式のデータをB方式のデータに変換だとか，画像データ内にある物の位置と種類を一覧出力だとか，こういうのが１単位になると．ここで考えてほしいのが，人間が動作として１段階としてやりうる動作の限界です．例えば，大きな生地を100gずつに切り分けタッパに入れる場合，人間は先ずチーズを２回たたきイタリア語で何か言い（すみません），（冗談です）100g分だと思う大きな生地を掴みそれがだいたい100g分かどうか判定し，そうでなければまた掴みなおして重量を検定し，そうであればそれをちぎって，タッパの入れる予定の場所を思い出してそこに生地を置く，これをタッパがいっぱいになるか生地がなくなるまでやります．これをプログラミング言語風に書くとだいたいこうでしょう．
　int i = 0;
　while(material.exist || !tapper.isFull) { //条件付け これをタッパがいっぱいになるか生地がなくなるまでやります
　 piece = material.grab(100); //100g分だと思う大きな生地を掴み
　 if(piece.weight <= 105 && piece.weight >= 95) { //それがだいたい100g分かどうか判定し
　 mat_small = piece.apart(); //そうであればそれをちぎって
　 whereto = tapper.point[i].pos; //タッパの入れる予定の場所を思い出して
　 mat_small.put(tapper, whereto); //そこに生地を置く
　 }
　 i += 1;
　 } else { //そうでなければ
　 piece.release(); //また掴みなおして
　 }
　}
　これなら何をしているか手順通りに適度に分解されて記述され，概ね明快です．特に，「material」は生地，「tapper」はタッパといった具合にそれぞれ構造体なのですが，その説明があるとなお明快でしょう．しかし，生成AIでのプログラミングではどうでしょうか．
　apart_material.c
　これで話が終わってしまいます．このapart_materlal.cが果たして本当にそうなのかは結局見ないとわかりません．こういう小さいのは，見るのであれば結局作ってしまったほうが途中で変更も効くしわざわざ脳内から言語化してそれを脳内言語に近しいようなものにすることがないわけです．ところが，実際は複雑なシステムですら今後は生成AIがこういう風に「出力」する（けど，もっともそれがコンピュータ処理の利点を引き出すには或る意味良い）わけですから，中身を見ようなんてのは作った人ですらそうそうすることがなくなるでしょう．成果物だけの世界になる．そうすると，中身に作る段階で直接触れない以上果たして本当に考えどおりの処理をやっているのか，なにか，どこかでデータをちょろまかしていないか，そういうのをきちんと確認することが今度は必要になる．中身を見て判断しようとすれば，予習なしのわけのわからない異常な問題数の試験を解くような羽目になる．AIにやらせるったって，そいつが本当に仕事をしているのかも，黒箱化されていて保証しきれない．生成AIだけでプログラムを打つ，その一筋だけで無理が生じるようにしか私は思えません．検証のやりやすさやそれを通じた成果物の品質保証，という意味では私はプログラミング言語から生成AIへの転移には，バイナリ・コーディングからプログラミング言語への転移とは相当に，それこそ「有意」なほどに差があると考えます．
　余談ですが，実はExcelはたまに計算結果を間違えます．小数点あたりの動作に謎の脆弱性があるようで，同じ数字を同じ式で電卓で計算してみるとたまにExcelとの間でコンマ2桁くらいの結果が違うことがあります．それ以来，私はExcelで小数を扱うときに重要なことであれば検算しますし，一回しかやらない表計算はものによっては手計算で済ますこともあります．小数点が関わる計算は「そんなものかぁ」というくらいの参考にとどめています．どれほど私が万物不信の気があるかがわかるかと思います．
　この記事をお読みになった方々の中には生成AIに対し私が喧嘩を売っているように見える方もいるかと思います．正直言いますが，生成AIが嫌いだったらもっと直接的な表現を使います．私のTwitterをご覧の方はわかるかと思いますが，私は昔よりはましになりましたが口汚い方です．そんな人間が論考じみた形で試みて書いているということは嫌いという単純な感情ではないし，ましてや喧嘩を売るということでもないです．散々思考を展開してきて言うのもなんですが，この記事って結局本職技術者として死産した人間がなんか遺言のつもりで喚いているだけなんですよね．それを使って真面目に論議するのはなんだか馬鹿らしいとすら思います．この文章は，そういう心意気で読むものです．しかしそれでも，私のいたずら心はこの注意書きを文頭に置くことを許していません．なぜなら，そういう視座でもう一回読んでほしいから．そして，もしこの記事を論文代わりか何かだと思っていたなら私が普段何かをするたびに感じている感情を，たまにはあなたにも味わってほしいから．
　私はめんどくさがりのくせによくこういうことを考えたり言ったりはするので，なおさら手のつけようがない．こんなんだからトラックに轢かれるわけです．
　今読み返してみると，思いの外生成AIのことを悪く言い過ぎたので私の（たいしたことない）活用例を話します．基本的には私の場合では生成AIはデバッガに専念してもらっています．Geminiはこちらから何も言わなくても原因を説いてくれますし，検索しろと言えば検索してくれます．GPTは検索で制限がかかるがために，尚更Geminiでやっています．必要部を抜き出したコードとエラー文章を書き出して質問すればだいたい的確な答えが解説付きで帰ってきます．勉強にもなるしこれは良いと思っているので，今後もやり続けます．（事実上検索用具として使っている側面が大きいのかもしれないですね．）また，自分が書いた文章の評論を書かせたり，他人が書いた風の自作文章を読み込ませてそれを徹底的に解剖させたり，遊びの範囲ではそれなりに使っています．
　しかしながら，それでも前述した生成AIで「すべてをつくる」段階には到底ついていけそうにありませんし，率直に言えば生成AI時代の技術稼業と私の技術稼業は価値観の根底から異なるわけです．私はかつて40代を自称していた時代がありましたが，身体的には兎も角それ以外では本当に20年遅れの部分があると思います．その遅れが前述の価値観相違などに現れているのだというのが，私の中での仮説です．
　そういうわけですので，技術者としては死んでいる，非効率な方法を取ったものづくりを私はやるでしょうが，それでもものを自作するということ自体に楽しみがあることもあるので，やめる気はありません．ましてや，本職としては不可逆的に死んだわけですし．
